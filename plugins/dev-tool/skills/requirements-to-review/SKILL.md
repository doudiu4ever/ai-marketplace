# 需求确认、实现与审核

按“需求讨论 → 确认并落盘 → 按用户选择的粒度实现、验证 → 循环审核全部未提交变更并修复 → 人工审核 → 授权提交”推进。只规定开发流程，不强制引入 worktree、TDD、子代理或过程中提交。

调查、记录和验证的深度随任务影响调整。简单修改保留必要判断即可；涉及跨版本、外部系统或复杂状态变化时再展开相应检查，不为每个任务增加完整矩阵或额外暂停点。

## 进入与恢复

- 先识别用户当前要讨论、实现、继续任务、审核，还是提交。读取已有任务文档和相关代码，沿用已获确认的需求、执行模式、审核方式及进度，不从头重复流程；若旧文档仅记录了审核工具而缺少用户确认或默认授权依据，视为待选择，在继续实现或审核前补确认一次，不重开已确认需求。
- 纯咨询直接回答；只读审核只产出审核结论，不修改代码、不运行嵌套审核，也不要求重新确认需求。
- 用户已明确确认需求或授权某一步时，直接执行该范围内的工作。仅在缺少会影响范围、验收、执行模式或审核方式的决定时提问。

## 1. 讨论并收敛需求

需求分析要发现缺失的决定，确定行为细节、收敛边界，形成可验证的共识。讨论深度随任务复杂度调整，不机械套用问题清单，也不能用一份看起来完整的 checklist 掩盖未澄清的需求。

### 理解问题与调查现状

- 用户提出需求后，先检查项目已有的文档目录和相关需求、设计或任务文档，了解已有决定及记录方式。结合主题关联、原文档用途和维护状态，判断适合在原文档追加或更新，还是另起新文档；不默认每个新需求都新建文档，也不因存在相关文档就直接追加。位置或组织方式有歧义时，给出建议并请用户决定；已有明确约定或指定位置时直接沿用。
- 先明确谁在什么场景下遇到什么问题、当前如何处理、希望改善什么，再讨论方案。用户提出的实现方式需结合目标评估；有矛盾时说明原因和取舍，不擅自替换用户已确认的选择。
- 根据需求定位可能涉及的用户入口、对象类型、主要调用链、模块职责与现有测试，形成初步改动范围。尤其检查用户用语是否包含项目中处理方式不同的对象或场景，及已有流程是否带有额外副作用；先查明这些事实，再提出会影响范围的问题，不等实现大体完成才发现边界。
- 区分已知事实、用户要求、尚未验证的假设及待决定的问题。能从项目查明的事情自行调查，不能把推测写成已确认需求；初步代码定位用于澄清需求，不代表用户已经授权所有相关模块的功能。
- 此阶段可以只读调查和编写需求草案，不修改实现代码。

### 澄清细节与边界

- 优先明确本次处理哪些对象、角色和使用场景，以及明确排除哪些分支。项目支持的全部类型不等于本次需求范围；有会改变方案的歧义时，结合实际代码给出具体选择和推荐边界，确认后再展开这些分支的异常处理。
- 围绕正常流程及会影响结果的异常、边界情况，用具体场景明确输入、预期输出、失败处理、暂停和恢复行为；仅讨论与任务相关的内容。
- 明确本次做什么、暂不做什么，以及继续沿用哪些现有行为。只展开会影响本次范围、关键行为或验收的问题；已排除的分支记录为非目标，不继续穷尽其细节，不附带无关重构、功能扩展或额外基础设施。
- 梳理关键问题之间的依赖，优先解决会改变实现方向的上游选择。每轮只问前提已明确的问题；互不依赖的问题可以合并，但保持数量适中。依赖未决选择或尚未查明事实的问题留到后续，不替用户假定答案，也不因此阻塞其他独立问题。
- 每个问题说明需要决定什么、为什么影响实现、可选方案及主要取舍，并给出推荐答案和理由。标明建议所依据的事实与假设，不把推荐选项当作已确认选择。产品行为、范围和重要取舍由用户决定，常规实现细节由 agent 自行处理。
- 每轮收到回答后，检查新决定带来的后续问题、排除的方案，以及与已有决定的冲突，再调整下一轮问题。发现矛盾时指出具体场景和影响，请用户澄清受影响的决定，不按静态清单机械追问。
- 沿用用户已有决定，及时记录关键选择及依据，不重复询问已确认事项。仍有不确定性时明确说明其影响，不把未获确认的建议当成决定。

### 复用与改动边界

- 需求规划和实现拆分沿用项目已有的模块职责、入口组织、命名、配置与测试习惯。优先通过现有接口或配置复用完整模块，并核对其前置条件、输出及副作用是否符合本次范围；不能为复用而把模块支持的全部场景带入需求。
- 仅需现有模块的一部分时，先评估已有接口、局部适配或小范围提取能否满足需求。比较这些选择对原调用方、行为和验证范围的影响，不默认复制实现，也不默认重构整个模块或建立新框架。
- 必要重构按影响判断大小，不按代码行数判断。涉及公共接口或兼容性变化、职责重划、多处调用方迁移或明显扩大验证范围的调整，应在需求阶段尽早列出具体受影响模块、理由、较小替代方案和验证计划，请用户确认后再实施；已有授权则直接沿用。实现中才发现时只暂停依赖该决定的部分。范围内、影响局部、保持既有调用行为且可明确验证的小调整可自行完成，记录原因和影响，并在最终交付中单列说明。

### 验收与收敛

- 确定方案前，检查现有能力、配置调整或更小的改动能否满足同样的验收条件。存在更简单的方案时说明取舍和建议，不擅自替换用户已确认的选择。
- 确认前结合初步代码定位做遗漏决策检查：对象和场景边界是否明确，关键行为是否依赖未说明的假设，已有决定是否互相矛盾，重要异常是否有明确结果，复用是否引入额外行为或尚未确认的大范围重构。发现缺口时按依赖顺序继续澄清；不因范围外分支未展开或常规实现细节未定而延长讨论。
- 先写可观察、可验证的验收条件，再拆实现 checklist；每个必要步骤应对应需求或验收条件。关键条件应对应适用阶段、预期状态、观测位置和判断方法，并说明将保留的证据；可用简短文字，不强制表格。涉及多处配置或异步生效时，按需求区分持久配置、运行状态与后续消费者实际读取的状态。预期结果依据需求确定，不能直接把实现当前输出当作正确答案。
- 进入实现前，目标、范围、非目标和关键行为应已明确，影响实现方向的关键问题已有决定，验收条件足以判断是否完成。剩余假设需说明，存在可能推翻方案的未决问题时继续澄清。
- 将收敛结果整理为需求与 checklist 草案供用户确认；已有明确确认的部分直接沿用。用户确认和必要执行选择齐备后，按约定模式推进。

## 2. 确认并保存任务文档

- **文档分层**：**主体需求文档**放在**项目 git 工作区内**（沿用项目目录与命名约定，不预设固定目录），随任务提交进 git 供追溯，也让无显式上下文的独立 reviewer 仅读未提交变更即可获知边界与裁定；与已有文档相关时建立引用。**过程细节记录**（逐轮审核原始报告与核查流水、修复中的详细测试数据与日志）严格放在 **git 仓库目录之外**，不进仓库追踪与提交。
- 主体文档按项目习惯记录需求、范围与非目标、关键决定及依据、剩余假设、验收条件、实现步骤、搬迁映射、执行模式、审核方式、概括性验证与审核记录和专门的审核忽略区（不强制分节）。修复项已有代码与需求变更，主体文档仅简要概括审出/修复/忽略了什么；忽略项写入“审核忽略区”留作追溯。每个 checklist 项须可验证，实现前写明完成条件、验证方式与预期证据。
- 长期或多阶段任务在主体文档保留当前有效摘要（适用版本/环境、有效与已取代决定、状态、剩余问题及验证结论）；冗长过程历史严格放 git 仓库目录之外。
- 草案先标“待确认”；用户明确确认后才标“已确认”并进入实现，记录确认依据，不虚构批准。
- 进入实现前，未确定的执行模式与审核方式随需求确认一并询问一次并写入文档；已指定则沿用，可随时切换：
  - **执行模式**（不默认全量）：
    - **逐步**：每项实现验证后审核全部未提交变更并修复；通过后更新文档、汇报并暂停，等确认再进下一项。
    - **全量**：连续实现并验证全部已确认项后统一审核修复循环；通过后交由人工验收。
  - **审核方式**：由本 skill 发起，按本机能力**平级**列出可选方案——**显式注入上下文的独立只读审核**（如宿主只读子代理、`codex review -`）与**不带显式上下文的未提交变更审核**（如 `codex review --uncommitted`）——由用户选择，注明特点、限制及是否涉及外部提供商/账号。确认后记录方式与依据；外部工具须记录已授权的提供商/账号标识（不含凭据），未经授权不得外发代码或文档，目标变更或无法核实时重新确认。
- 实现中事实与假设不符时评估影响；需改范围、对外行为或验收条件时回到相关点取得确认再更新文档，常规实现选择自行处理。

推荐精简结构（按实际任务填写，不留空栏目）：

```markdown
# <需求名称>

状态：待确认 / 实现中 / 审核中 / 待人工审核 / 待授权提交 / 已完成 / 受阻
需求确认依据：<用户确认记录；未确认写待确认>
执行模式：逐步 / 全量 / 待选择
当前实现范围：<当前 / 全部 checklist 项>
审核范围：全部未提交变更（已暂存、未暂存及未跟踪内容）
审核方式：<工具、调用方式及确认依据（外部工具另记已授权提供商/账号，不含凭据），或待选择>

## 需求与范围
<目标、边界、约束与非目标；复用、改动与重构决定>

## 验收条件
- <预期结果、阶段、观测与判断方式、预期证据>

## 实现 checklist
- [ ] <必要步骤、完成条件及验证方式>

## 验证与审核记录
<验证结论及审出/修复/忽略摘要与阻塞；逐轮审核原始流水与详细测试数据严格保存在 git 仓库目录之外>

## 审核忽略区
本区为已裁定暂缓/忽略项，随任务提交进 git 供追溯；独立审核仅在新改动或新证据表明影响超出下列边界时重开，不对忽略区文案做次生审查。
<原始发现、位置、严重程度、类别、依据、残留影响、首次轮次及人工决定（待确认 / 维持忽略 / 重新开启）>

## 人工审核与交付
<人工审核结论；commit、push 授权及执行状态>
```

## 3. 按 checklist 实现

- 开始时查看工作区状态，识别已有变更，不覆盖或撤销用户的工作。逐步模式在每项开始时记录该项与已有变更的边界，供判断问题归属和修复权限，不用于缩小审核范围；同一文件可能包含多项变更，不能只靠文件名划分。
- 选择满足已确认需求的简单实现；新增抽象、扩展点或配置选项应有具体需求或项目现有约束作为依据，不为假想的未来用途提前泛化。简单不等于行数最少，不能牺牲可读性、必要的错误处理或兼容性。
- 每处改动应能对应到当前任务及必要关联影响。沿用项目风格，不顺手重构相邻代码、统一无关格式或清理历史问题；清理由本次修改产生的无用代码，既有无关问题单独记录。
- 搬迁、拆分或重命名时记录“原位置 → 新位置”映射。原样迁移的部分以原文核对，有意调整的部分按已确认需求验证。
- 按任务依赖推进，分别记录实现、验证与审核进度。只有对应项的实现、验证完成且全部未提交变更的审核循环通过后才标记完成；全量模式在统一审核通过前保留“已实现、待审核”的状态。
- 按项目要求和变更性质选择验证：修复 bug 时用复现步骤或回归测试证明问题已消除，重构时验证既有行为保持一致，不强制所有任务采用 TDD。测试、检查及必要文档更新属于实现步骤，记录实际证据，不以“以后再验证”标记完成。
- 每步及时更新进度和有影响的决定，保证换会话后能从文档继续。
- 逐步模式的授权覆盖当前项的实现、验证，以及本次任务已实现各项的审核修复；全量模式覆盖全部已确认项。审核全部未提交变更不代表可以修改无关既有工作或提前实现后续项；两种模式均不包含 commit、push。

### 验证结果与证据

- 检查关键验收条件是否实际被观测和判断，区分未覆盖、失败、条件通过及通过。命令成功、服务就绪和测试数量只证明各自检查的内容；模拟测试、单模块测试和完整入口实测分别说明，不能相互冒充。
- 用于形成验收结论的采集器、判定脚本和测试控制器也属于验证范围。按风险为关键判断构造代表性的错误状态、缺失数据或采集失败，确认不能误判通过；预期失败场景核对失败原因、停止位置及副作用。控制外部操作的测试工具还需验证必要的中断、恢复和结果保存行为，避免到长时间实测收尾才检查工具可靠性。
- 证据注明足以判定适用性的代码版本或工作区状态、关键配置与环境、执行入口和观测阶段。临时准备、替代组件或绕过操作的影响应单列，不能将其条件下的结果推广为默认行为；异步或长时间操作的中间观测不能替代完成后的验收。
- 实现、配置、采集或判断变化后评估受影响证据：可复用说明依据，可重算重新判断，缺观测补采补测，不机械重跑无关验证。详细测试数据、完整日志与中间产物严格保存在 **git 仓库目录之外**供人工核查，主体需求文档保留简洁自洽的验证结论与修正摘要，不以未经核实的“通过”替代观测，也不在仓库留失效临时链接。

## 4. 循环审核未提交变更

逐步模式在当前项验证后进入审核，全量模式在全部项验证后进入审核。两种模式都向 reviewer 提供全部未提交变更，以便沿实际调用关系判断影响。已授权的审核与修复连续推进。

### 审核口径

- 从已确认的需求和用户入口出发，先走通主流程，再看这次改动触及的常见失败路径。经验用来选择检查点。例如，调用方会重试，就检查失败后重试会不会重复写入。只展开当前调用方式、支持的输入或使用记录能说明的场景。
- 报告问题时指出触发它的输入或操作、出错位置、预期与实际结果，以及对验收或已有功能的具体影响。代码调用链、文档中的流程或测试结果都可作为依据，无需等到线上发生。低频但有明确触发路径的严重回归也按此标准处理。
- 如果结论依赖未经支持的用法、缺乏依据的异常组合，或只剩风格偏好、未来扩展和通用加固建议，就结束这条线索。测试脚手架仅核对**假阳性（误判通过）、宿主机/仓库副作用、标准测试环境可运行性**，非常规极端环境变量或特殊路径字符防御不作为阻塞项。主体文档中的“审核忽略区”和简要审核记录作为裁定输入，不对忽略区文案本身做次生审查；已忽略项仅在新改动或新证据表明存在超出记录边界的实质影响时重开。审核结束时，reviewer 报告本轮问题清单，或明确给出“本轮无问题”结论。

### 调用审核

- 由本 skill 发起，遵循已确认或授权的审核方式（缺授权依据先补确认；外部工具目标变更或无法核实时重新确认），记录实际工具、方式及依据。**显式注入上下文**与**不带显式上下文的未提交变更审核（如 `codex review --uncommitted`）**平级可选，由用户选择；三端均可完成审核，不要求额外安装客户端或默认多端重复审核。详见 [references/review-invocation.md](references/review-invocation.md)。
- 两种方式均须覆盖最新裁定上下文：带上下文方式每轮传入审核口径、需求与非目标、验收条件、checklist 进度（逐步模式标明未实施项）、变更边界、搬迁映射、简要修复记录及忽略区；不带上下文方式依托工作区内同步更新的主体需求文档（含简要记录与审核忽略区）随未提交变更一并读取。原样搬迁核对等价性，有意改动按验收条件判断。
- 须覆盖全部已暂存、未暂存及未跟踪内容，不能只看局部 `git diff` 或按当前项截取。reviewer 无法直读工作区时提供完整差异、未跟踪内容与必要上下文；材料缺失不得宣称审核通过。
- 沿受影响用户入口读取必要既有实现，核对组合行为与验收条件。详细测试数据与逐轮审核原始流水严格放在 **git 仓库目录之外**，不进仓库；带上下文时按需提供脱敏证据，无上下文时由主体文档简要结论承接，不为审核把过程日志、环境数据或凭据放入仓库。
- 核对已有证据能否证明关键行为，指出缺口时写明缺少验证的需求或可能误判通过的错误；迁移或跨版本适配按约定保留行为核对。
- reviewer 只读检查，不修改、不提交、不嵌套审核。按宿主能力限制写权限，由实现方修复；报告须写明范围、位置与依据、严重程度及未验证部分。进程正常退出不代表通过。

### 处理每轮结果

1. 等待独立审核结束，将本轮原始细节报告与逐项核查流水记在 **git 仓库目录之外**的过程文档中；核实全部发现后，在工作区主体文档的“验证与审核记录”更新概括摘要（审出/修复/忽略了什么及当前阻塞）。
2. 对范围内实际错误做最小修复，对关键验收缺口补验；修复项已体现于代码与需求变更，主体文档仅简要记录，修复细节测试数据严格放 git 仓库目录之外。同根因一次修正并复验，上轮引入的回归一并处理。**第 2 轮起先做次生发散自检**：若新发现由上轮防护引出或简化多余防护即可消除，按次生发散简化或归入忽略区，停止打补丁。生产代码无问题、仅剩测试脚手架或 P3 边缘项时优先忽略收口。
3. 暂缓修复的发现记入工作区主体文档专门的“审核忽略区”待人工确认（随任务提交进 git 供追溯及下轮读取），同类重复关联原记录：
   - **超范围**：不对应本次需求、验收或本次引入的回归（含既有缺陷、无关变更、变更需求或提前做后续项）；
   - **次生发散**：原问题已解决，后续建议仅在叠加新假设或前序防护链式反应下才有收益。停止追加防护，连同起因归为一类；多余防护可简化并复验；
   - **过度打磨**：不支持用法外的假设叠加、测试脚手架非常规极端环境防御，或风格/泛化加固建议；
   - **误报**与**用户裁定忽略**。

   归类须写明共同触发前提、暂缓理由和适用边界，关联原始发现、位置、严重程度、残留影响及首次轮次；后续相似项仅在符合依据时沿用。本次引入的安全或数据风险按真实回归处理；既有安全或数据风险按超范围记录并交付置顶标注。
4. **本轮只要报出问题或建议，逐项处理后就发起下一轮独立审核。** 即使全部归入忽略区、代码未改动，也在更新工作区审核忽略区与简要记录后复审，直到 reviewer 明确报告无问题。带上下文时传入最新未提交变更、上轮报告、处理结果、最新忽略区及已审未改的生产代码范围；不带上下文时通过工作区更新后的主体文档与忽略区传递最新裁定。重复忽略项仍适用原依据时关联原条目并标明边界继续复审，交付时统一由用户确认。
5. **仅当最新一轮独立 reviewer 覆盖全部未提交变更与最新审核忽略区后明确报告无问题，且必要验证通过，才结束循环进入人工审核。** 以正文实际输出为准；仍有问题或建议则回到第 1 步。通过后将概括结论记入主体文档并交付（逐步模式待确认下一项，全量模式交付全部结果，完整汇报忽略区条目供用户决定是否重开）。

- 验收受阻需用户决定时说明影响与缺失输入。仅在修复互相冲突，或同一待修实质问题连续两轮无进展时暂停交由用户决定；已忽略项重复报告按第 4 步自动复审，不因总轮次中断。

## 5. 人工审核与授权交付

- 独立审核通过后标“待人工审核”。总结报告提供工作区主体需求文档（含简要验证与审核记录、末轮结论摘要及审核忽略区）、变更摘要，并按需说明 git 仓库目录之外的过程细节与测试数据位置。合并忽略条目按组说明共同理由与边界，列全原始发现、严重程度、位置及残留影响，既有安全或数据风险置顶。续接旧任务汇总已有暂缓项。逐步模式明确当前项与下一项，末项通过交付整体总结。
- 单列本次为复用做的既有模块调整或重构（必要性、影响范围、原调用方行为是否保持及验证结果，含自行完成的小调整）；无此类改动不留空栏目。验证结论保留适用条件与未覆盖项。
- 用户可维持忽略或重开条目。在主体文档记录决定并保留原记录，重开项移出有效忽略范围，修复验证后重走第 4 节审核循环再交人工确认。
- 整体人工审核通过后，仅在取得明确授权时执行 commit 或 push（分别按授权范围；确认进入下一项不等于授权提交；用户自行提交亦有效）。提交时，工作区主体需求文档（含简要记录与审核忽略区）随代码一并提交进 git 供追溯；仓库目录之外的过程细节与详细测试数据不进入提交。
- 人工审核通过但未授权提交时记“待授权提交”，不把单项完成、审核通过与已提交混为一谈。

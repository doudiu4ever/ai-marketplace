# 需求确认、实现与审核

按“需求讨论 → 确认并落盘 → 按用户选择的粒度实现、验证并循环审核修复 → 人工审核 → 授权提交”推进。只规定开发流程，不额外引入 worktree、强制 TDD、子代理或过程中提交。

## 进入与恢复

- 先识别用户当前要讨论、实现、继续任务、审核，还是提交。读取已有任务文档和相关代码，沿用已有确认、执行模式及进度，不从头重复流程。
- 纯咨询直接回答；只读审核只产出审核结论，不修改代码、不运行嵌套审核，也不要求重新确认需求。
- 用户已明确确认需求或授权某一步时，直接执行该范围内的工作。仅在缺少会影响范围、验收或执行模式的决定时提问。

## 1. 讨论并收敛需求

需求分析要发现缺失的决定，确定行为细节、收敛边界，形成可验证的共识。讨论深度随任务复杂度调整，不机械套用问题清单，也不能用一份看起来完整的 checklist 掩盖未澄清的需求。

### 理解问题与调查现状

- 用户提出需求后，先检查项目已有的文档目录和相关需求、设计或任务文档，了解已有决定及记录方式。结合主题关联、原文档用途和维护状态，判断适合在原文档追加或更新，还是另起新文档；不默认每个新需求都新建文档，也不因存在相关文档就直接追加。位置或组织方式有歧义时，给出建议并请用户决定；已有明确约定或指定位置时直接沿用。
- 先明确谁在什么场景下遇到什么问题、当前如何处理、希望改善什么，再讨论方案。用户提出的实现方式需结合目标评估；有矛盾时说明原因和取舍，不擅自替换用户已确认的选择。
- 阅读相关代码、现有行为、文档和约束，区分已知事实、用户要求、尚未验证的假设及待决定的问题。能从项目查明的事情自行调查，不能把推测写成已确认需求。
- 此阶段可以只读调查和编写需求草案，不修改实现代码。

### 澄清细节与边界

- 围绕正常流程及会影响结果的异常、边界情况，用具体场景明确输入、预期输出、失败处理、暂停和恢复行为；仅讨论与任务相关的内容。
- 明确本次做什么、暂不做什么，以及继续沿用哪些现有行为。只展开会影响本次范围、关键行为或验收的问题；已排除的分支记录为非目标，不继续穷尽其细节，不附带无关重构、功能扩展或额外基础设施。
- 梳理关键问题之间的依赖，优先解决会改变实现方向的上游选择。每轮只问前提已明确的问题；互不依赖的问题可以合并，但保持数量适中。依赖未决选择或尚未查明事实的问题留到后续，不替用户假定答案，也不因此阻塞其他独立问题。
- 每个问题说明需要决定什么、为什么影响实现、可选方案及主要取舍，并给出推荐答案和理由。标明建议所依据的事实与假设，不把推荐选项当作已确认选择。产品行为、范围和重要取舍由用户决定，常规实现细节由 agent 自行处理。
- 每轮收到回答后，检查新决定带来的后续问题、排除的方案，以及与已有决定的冲突，再调整下一轮问题。发现矛盾时指出具体场景和影响，请用户澄清受影响的决定，不按静态清单机械追问。
- 沿用用户已有决定，及时记录关键选择及依据，不重复询问已确认事项。仍有不确定性时明确说明其影响，不把未获确认的建议当成决定。

### 验收与收敛

- 确定方案前，检查现有能力、配置调整或更小的改动能否满足同样的验收条件。存在更简单的方案时说明取舍和建议，不擅自替换用户已确认的选择。
- 确认前做一次遗漏决策检查：关键行为是否依赖未说明的假设，已有决定是否互相矛盾，范围内的重要异常和边界场景是否有明确结果。发现缺口时按依赖顺序继续澄清；不因范围外分支未展开或常规实现细节未定而延长讨论。
- 先写可观察、可验证的验收条件，再拆实现 checklist。验收条件描述应达到的结果，checklist 描述完成工作的步骤；必要步骤应能对应到需求或验收条件。
- 进入实现前，目标、范围、非目标和关键行为应已明确，影响实现方向的关键问题已有决定，验收条件足以判断是否完成。剩余假设需说明，存在可能推翻方案的未决问题时继续澄清。
- 将收敛结果整理为需求与 checklist 草案供用户确认；已有明确确认的部分直接沿用。用户确认和必要执行选择齐备后，按约定模式推进。

## 2. 确认并保存任务文档

- 按需求分析阶段确定的记录位置和方式，追加或更新原文档，或创建新文档。沿用项目已有的目录、命名和组织约定，不预设或强制创建固定目录；新建文档与已有文档相关时建立必要引用，避免重复维护同一份需求。
- 按项目文档组织方式记录已确认的需求、范围与非目标、关键决定及依据、剩余假设、验收条件、必要实现步骤、执行模式和审核记录；不强制为每类内容单独设章节。每个 checklist 项应是可以验证的工作单元，实现前写明完成条件、验证方式及预期证据。
- 可以先保存标记为“待确认”的草案；只有用户明确确认后，才能标记为“已确认”并进入实现。记录确认依据，不虚构用户批准。
- 与用户确定执行模式，并记录在文档中：
  - **逐步**：以当前一个 checklist 项为单位，完成实现和验证后，自动进入该项的审核与修复循环；通过后更新文档、汇报并暂停，等待用户确认才进入下一项。
  - **全量**：连续实现全部已确认的 checklist 项并完成必要验证，再对本次需求的全部变更统一循环审核与修复；通过后交由用户验收，不在每项完成时暂停或单独启动审核循环。
- 模式尚未确定时询问一次，不擅自默认为全量。已指定的模式持续有效，用户可随时切换。
- 实现中发现事实与假设不符时，评估影响；若需要改变范围、对外行为或验收条件，回到相关需求点说明影响并取得确认，再更新文档，不重启全部讨论。已确认范围内的常规实现选择自行处理。

推荐使用以下精简结构，按实际任务填写，不保留无用栏目：

```markdown
# <需求名称>

状态：待确认 / 实现中 / 审核中 / 待人工审核 / 待授权提交 / 已完成 / 受阻
需求确认依据：<用户确认记录；尚未确认时明确写待确认>
执行模式：逐步 / 全量 / 待选择
当前工作与审核范围：<当前 checklist 项 / 本次需求全部 checklist 项>
审核方式：自动 CLI / 手动交互

## 需求与范围
<目标、预期行为、约束、边界和明确不做的内容>

## 验收条件
- <可观察、可验证的条件>

## 实现 checklist
- [ ] <必要步骤、完成条件及验证方式>

## 验证与审核记录
<验证结果；每轮审核的范围、结论、问题和处理结果；当前阻塞>

## 人工审核与交付
<人工审核结论；commit、push 的授权及实际执行状态>
```

## 3. 按 checklist 实现

- 开始时查看工作区状态，识别已有变更，不覆盖或撤销用户的工作。逐步模式在每项开始时记录该项与已有变更的边界，供审核区分；同一文件可能包含多项变更，不能只靠文件名划分。
- 选择满足已确认需求的简单实现；新增抽象、扩展点或配置选项应有具体需求或项目现有约束作为依据，不为假想的未来用途提前泛化。简单不等于行数最少，不能牺牲可读性、必要的错误处理或兼容性。
- 每处改动应能对应到当前任务及必要关联影响。沿用项目风格，不顺手重构相邻代码、统一无关格式或清理历史问题；清理由本次修改产生的无用代码，既有无关问题单独记录。
- 按任务依赖推进，分别记录实现、验证与审核进度。只有对应粒度的实现、验证和审核循环均通过后才标记完成；全量模式在统一审核通过前保留“已实现、待审核”的状态。
- 按项目要求和变更性质选择验证：修复 bug 时用复现步骤或回归测试证明问题已消除，重构时验证既有行为保持一致，不强制所有任务采用 TDD。测试、检查及必要文档更新属于实现步骤，记录实际证据，不以“以后再验证”标记完成。
- 每步及时更新进度和有影响的决定，保证换会话后能从文档继续。
- 逐步模式的授权覆盖当前项的实现、验证和审核修复，全量模式覆盖全部已确认项；两种模式均不包含 commit、push。

## 4. 循环审核未提交变更

审核粒度由用户选择的执行模式决定：逐步模式在当前项实现并验证后立即审核该项，全量模式在全部项实现并验证后统一审核。进入对应粒度的审核循环不再单独请求确认，范围内的修复与重新审核连续推进。

### 调用审核

- 默认使用自动 CLI：先确认当前环境 `codex review --help` 支持所需参数，再按审核粒度选择调用方式。
- 逐步模式使用自定义审核提示（例如通过 `codex review -` 从标准输入读取），明确当前 checklist 项、验收条件、变更边界及相关文档。审核当前项的完整变更和必要关联影响，不把尚未实施的其他项当作当前项的缺陷，也不要求为审核提前实现下一项。
- 全量模式可执行 `codex review --uncommitted`，审核本次需求的全部未提交变更。让审核方能读取已确认的需求文档及验收条件，并区分工作区中的无关既有变更。
- 两种模式都应检查范围内已暂存、未暂存及未跟踪的内容，不能只看 `git diff`。按当前 CLI 支持的方式提供上下文；不假定自定义 prompt 能与 `--uncommitted` 组合使用。
- 审核同时检查改动与当前任务的对应关系，识别无关修改和缺乏需求依据的复杂度；不能只因个人风格偏好或代码行数较多就要求重写。
- 用户明确要求手动 `/review` 时，等待其在 Codex 交互界面发起符合当前粒度的审核，读取该轮结果后继续。不要把 `/review` 当成 shell 命令。
- 只读 reviewer 的任务仅限审核并报告问题，不能调用本循环再次启动 reviewer。
- 当前环境无法调用 Codex 或审核结果不可获得时，记录审核受阻并说明所需操作；普通自查不能冒充一次 Codex review。

### 处理每轮结果

1. 等待审核完整结束，读取真实结论并简要记录范围和发现。进程退出成功不等于没有问题。
2. 核实发现，以足以解决问题的最小必要改动修复当前审核范围内的有效问题，并执行受影响的验证；不能借审核扩展功能或重做架构，也不能以控制改动为由保留有效问题。范围外的问题记录后交用户决定，不自行扩大当前项或提前实现其他项。
3. 对误报说明可复核的依据；不能自行降低严重程度、隐藏发现或以“不是阻塞级别”跳过有效问题。
4. 每次修复后，按同一粒度重新审核最新完整变更，不只复查上轮指出的片段；逐步模式保持当前项及其关联影响的范围，全量模式覆盖本次需求全部变更。
5. 仅当最新一轮审核完整完成、当前范围内没有待解决问题且必要验证通过，才进入人工审核。逐步模式到此必须暂停，等待用户确认下一项；全量模式到此交付全部结果。存在尚未澄清的范围内争议时不能标记审核通过。

- 不用固定轮数代替通过条件。若连续两轮出现同一问题且没有实质进展、修复互相冲突或需要用户决策，记录受阻并请求决定，不无限重试，也不宣称通过。
- 文档中记录每轮简短结论即可。最终仅追加审核记录不触发记录自身的无限审核循环；代码、配置、需求或其他实质内容再次变化时必须重新审核。

## 5. 人工审核与授权交付

- 对应粒度的自动审核通过后标记“待人工审核”，提供需求文档、变更摘要、验证结果和最新审核结论，保留未提交变更供用户检查。逐步模式明确已完成的当前项和待确认的下一项，不能自动继续；最后一项通过后交付整体结果。
- “最新审核未发现问题”不等于证明没有缺陷，不用该表述替代人工审核。
- 用户提出修改时完成必要确认、实现及验证，按当前粒度重新进入审核循环，然后再次交由人工审核。
- 整体人工审核通过后，只有取得用户明确授权才执行 commit 或 push；分别按授权范围执行。确认进入下一项不等于授权提交。用户自行提交也是有效交付方式。
- 整体人工审核通过但未授权提交时记录“待授权提交”。交付状态以实际结果为准，不把单项完成、整体审核通过和已提交混为一谈。

# 需求确认、实现与审核

按“需求讨论 → 确认并落盘 → 按用户选择的粒度实现、验证 → 循环审核全部未提交变更并修复 → 人工审核 → 授权提交”推进。只规定开发流程，不强制引入 worktree、TDD、子代理或过程中提交。

调查、记录和验证的深度随任务影响调整。简单修改保留必要判断即可；涉及跨版本、外部系统或复杂状态变化时再展开相应检查，不为每个任务增加完整矩阵或额外暂停点。

## 进入与恢复

- 先识别用户当前要讨论、实现、继续任务、审核，还是提交。读取已有任务文档和相关代码，沿用已有确认、执行模式及进度，不从头重复流程。
- 纯咨询直接回答；只读审核只产出审核结论，不修改代码、不运行嵌套审核，也不要求重新确认需求。
- 用户已明确确认需求或授权某一步时，直接执行该范围内的工作。仅在缺少会影响范围、验收或执行模式的决定时提问。

## 1. 讨论并收敛需求

需求分析要发现缺失的决定，确定行为细节、收敛边界，形成可验证的共识。讨论深度随任务复杂度调整，不机械套用问题清单，也不能用一份看起来完整的 checklist 掩盖未澄清的需求。

### 理解问题与调查现状

- 用户提出需求后，先检查项目已有的文档目录和相关需求、设计或任务文档，了解已有决定及记录方式。结合主题关联、原文档用途和维护状态，判断适合在原文档追加或更新，还是另起新文档；不默认每个新需求都新建文档，也不因存在相关文档就直接追加。位置或组织方式有歧义时，给出建议并请用户决定；已有明确约定或指定位置时直接沿用。
- 先明确谁在什么场景下遇到什么问题、当前如何处理、希望改善什么，再讨论方案。用户提出的实现方式需结合目标评估；有矛盾时说明原因和取舍，不擅自替换用户已确认的选择。
- 根据需求定位可能涉及的用户入口、对象类型、主要调用链、模块职责与现有测试，形成初步改动范围。尤其检查用户用语是否包含项目中处理方式不同的对象或场景，及已有流程是否带有额外副作用；先查明这些事实，再提出会影响范围的问题，不等实现大体完成才发现边界。
- 区分已知事实、用户要求、尚未验证的假设及待决定的问题。能从项目查明的事情自行调查，不能把推测写成已确认需求；初步代码定位用于澄清需求，不代表用户已经授权所有相关模块的功能。
- 此阶段可以只读调查和编写需求草案，不修改实现代码。

### 澄清细节与边界

- 优先明确本次处理哪些对象、角色和使用场景，以及明确排除哪些分支。项目支持的全部类型不等于本次需求范围；有会改变方案的歧义时，结合实际代码给出具体选择和推荐边界，确认后再展开这些分支的异常处理。
- 围绕正常流程及会影响结果的异常、边界情况，用具体场景明确输入、预期输出、失败处理、暂停和恢复行为；仅讨论与任务相关的内容。
- 明确本次做什么、暂不做什么，以及继续沿用哪些现有行为。只展开会影响本次范围、关键行为或验收的问题；已排除的分支记录为非目标，不继续穷尽其细节，不附带无关重构、功能扩展或额外基础设施。
- 梳理关键问题之间的依赖，优先解决会改变实现方向的上游选择。每轮只问前提已明确的问题；互不依赖的问题可以合并，但保持数量适中。依赖未决选择或尚未查明事实的问题留到后续，不替用户假定答案，也不因此阻塞其他独立问题。
- 每个问题说明需要决定什么、为什么影响实现、可选方案及主要取舍，并给出推荐答案和理由。标明建议所依据的事实与假设，不把推荐选项当作已确认选择。产品行为、范围和重要取舍由用户决定，常规实现细节由 agent 自行处理。
- 每轮收到回答后，检查新决定带来的后续问题、排除的方案，以及与已有决定的冲突，再调整下一轮问题。发现矛盾时指出具体场景和影响，请用户澄清受影响的决定，不按静态清单机械追问。
- 沿用用户已有决定，及时记录关键选择及依据，不重复询问已确认事项。仍有不确定性时明确说明其影响，不把未获确认的建议当成决定。

### 复用与改动边界

- 需求规划和实现拆分沿用项目已有的模块职责、入口组织、命名、配置与测试习惯。优先通过现有接口或配置复用完整模块，并核对其前置条件、输出及副作用是否符合本次范围；不能为复用而把模块支持的全部场景带入需求。
- 仅需现有模块的一部分时，先评估已有接口、局部适配或小范围提取能否满足需求。比较这些选择对原调用方、行为和验证范围的影响，不默认复制实现，也不默认重构整个模块或建立新框架。
- 必要重构按影响判断大小，不按代码行数判断。涉及公共接口或兼容性变化、职责重划、多处调用方迁移或明显扩大验证范围的调整，应在需求阶段尽早列出具体受影响模块、理由、较小替代方案和验证计划，请用户确认后再实施；已有授权则直接沿用。实现中才发现时只暂停依赖该决定的部分。范围内、影响局部、保持既有调用行为且可明确验证的小调整可自行完成，记录原因和影响，并在最终交付中单列说明。

### 验收与收敛

- 确定方案前，检查现有能力、配置调整或更小的改动能否满足同样的验收条件。存在更简单的方案时说明取舍和建议，不擅自替换用户已确认的选择。
- 确认前结合初步代码定位做遗漏决策检查：对象和场景边界是否明确，关键行为是否依赖未说明的假设，已有决定是否互相矛盾，重要异常是否有明确结果，复用是否引入额外行为或尚未确认的大范围重构。发现缺口时按依赖顺序继续澄清；不因范围外分支未展开或常规实现细节未定而延长讨论。
- 先写可观察、可验证的验收条件，再拆实现 checklist；每个必要步骤应对应需求或验收条件。关键条件应对应适用阶段、预期状态、观测位置和判断方法，并说明将保留的证据；可用简短文字，不强制表格。涉及多处配置或异步生效时，按需求区分持久配置、运行状态与后续消费者实际读取的状态。预期结果依据需求确定，不能直接把实现当前输出当作正确答案。
- 进入实现前，目标、范围、非目标和关键行为应已明确，影响实现方向的关键问题已有决定，验收条件足以判断是否完成。剩余假设需说明，存在可能推翻方案的未决问题时继续澄清。
- 将收敛结果整理为需求与 checklist 草案供用户确认；已有明确确认的部分直接沿用。用户确认和必要执行选择齐备后，按约定模式推进。

## 2. 确认并保存任务文档

- 按需求分析阶段确定的记录位置和方式，追加或更新原文档，或创建新文档。沿用项目已有的目录、命名和组织约定，不预设或强制创建固定目录；新建文档与已有文档相关时建立必要引用，避免重复维护同一份需求。
- 按项目文档组织方式记录已确认的需求、范围与非目标、关键决定及依据、剩余假设、验收条件、必要实现步骤、执行模式和审核记录；不强制为每类内容单独设章节。每个 checklist 项应是可以验证的工作单元，实现前写明完成条件、验证方式及预期证据。
- 长期或多阶段任务保留简短的当前有效摘要，列出适用版本或环境、有效决定、已取代决定、当前状态、剩余问题及证据入口；详细历史单独保留或链接，不让恢复会话必须从完整流水记录推断最新范围。
- 可以先保存标记为“待确认”的草案；只有用户明确确认后，才能标记为“已确认”并进入实现。记录确认依据，不虚构用户批准。
- 与用户确定执行模式，并记录在文档中：
  - **逐步**：以当前一个 checklist 项为单位，完成实现和验证后，自动对全部未提交变更进入审核与修复循环；通过后更新文档、汇报并暂停，等待用户确认才进入下一项。
  - **全量**：连续实现全部已确认的 checklist 项并完成必要验证，再对全部未提交变更进入审核与修复循环；通过后交由用户验收，不在每项完成时暂停或单独启动审核循环。
- 模式尚未确定时询问一次，不擅自默认为全量。已指定的模式持续有效，用户可随时切换。
- 实现中发现事实与假设不符时，评估影响；若需要改变范围、对外行为或验收条件，回到相关需求点说明影响并取得确认，再更新文档，不重启全部讨论。已确认范围内的常规实现选择自行处理。

推荐使用以下精简结构，按实际任务填写，不保留无用栏目：

```markdown
# <需求名称>

状态：待确认 / 实现中 / 审核中 / 待人工审核 / 待授权提交 / 已完成 / 受阻
需求确认依据：<用户确认记录；尚未确认时明确写待确认>
执行模式：逐步 / 全量 / 待选择
当前实现范围：<当前 checklist 项 / 本次需求全部 checklist 项>
审核范围：全部未提交变更（已暂存、未暂存及未跟踪内容）
审核方式：<审核工具及调用方式，如 Claude Code 只读 reviewer / Codex CLI / 手动独立会话>

## 需求与范围
<目标、对象与场景边界、约束及非目标；拟复用模块、必要改动与重构决定>

## 验收条件
- <预期结果及适用阶段、观测与判断方式、预期证据>

## 实现 checklist
- [ ] <必要步骤、完成条件及验证方式>

## 验证与审核记录
<验证结果及适用范围、证据位置；每轮审核的范围、结论、问题和处理结果；当前阻塞>

## 人工审核与交付
<人工审核结论；commit、push 的授权及实际执行状态>
```

## 3. 按 checklist 实现

- 开始时查看工作区状态，识别已有变更，不覆盖或撤销用户的工作。逐步模式在每项开始时记录该项与已有变更的边界，供判断问题归属和修复权限，不用于缩小审核范围；同一文件可能包含多项变更，不能只靠文件名划分。
- 选择满足已确认需求的简单实现；新增抽象、扩展点或配置选项应有具体需求或项目现有约束作为依据，不为假想的未来用途提前泛化。简单不等于行数最少，不能牺牲可读性、必要的错误处理或兼容性。
- 每处改动应能对应到当前任务及必要关联影响。沿用项目风格，不顺手重构相邻代码、统一无关格式或清理历史问题；清理由本次修改产生的无用代码，既有无关问题单独记录。
- 按任务依赖推进，分别记录实现、验证与审核进度。只有对应项的实现、验证完成且全部未提交变更的审核循环通过后才标记完成；全量模式在统一审核通过前保留“已实现、待审核”的状态。
- 按项目要求和变更性质选择验证：修复 bug 时用复现步骤或回归测试证明问题已消除，重构时验证既有行为保持一致，不强制所有任务采用 TDD。测试、检查及必要文档更新属于实现步骤，记录实际证据，不以“以后再验证”标记完成。
- 每步及时更新进度和有影响的决定，保证换会话后能从文档继续。
- 逐步模式的授权覆盖当前项的实现、验证，以及本次任务已实现各项的审核修复；全量模式覆盖全部已确认项。审核全部未提交变更不代表可以修改无关既有工作或提前实现后续项；两种模式均不包含 commit、push。

### 验证结果与证据

- 检查关键验收条件是否实际被观测和判断，区分未覆盖、失败、条件通过及通过。命令成功、服务就绪和测试数量只证明各自检查的内容；模拟测试、单模块测试和完整入口实测分别说明，不能相互冒充。
- 用于形成验收结论的采集器、判定脚本和测试控制器也属于验证范围。按风险为关键判断构造代表性的错误状态、缺失数据或采集失败，确认不能误判通过；预期失败场景核对失败原因、停止位置及副作用。控制外部操作的测试工具还需验证必要的中断、恢复和结果保存行为，避免到长时间实测收尾才检查工具可靠性。
- 证据注明足以判定适用性的代码版本或工作区状态、关键配置与环境、执行入口和观测阶段。临时准备、替代组件或绕过操作的影响应单列，不能将其条件下的结果推广为默认行为；异步或长时间操作的中间观测不能替代完成后的验收。
- 实现、配置、采集方式或判断逻辑变化后，评估受影响的证据：可复用的说明依据，可重算的重新判断，缺少观测的补采或补测，不机械重跑无关验证。保留原始结果，追加修正结论；支撑结论的相关脚本和脱敏证据应可定位、读取，不能只留下通过摘要或失效的临时路径。

## 4. 循环审核未提交变更

执行模式只决定实现粒度、进入审核的时机及暂停点：逐步模式在当前项实现并验证后进入审核，全量模式在全部项实现并验证后进入审核。两种模式每轮都审核全部未提交变更，包括此前已通过审核的项及各项之间的关联影响。进入审核循环不再单独请求确认，已授权范围内的修复与重新审核连续推进。

### 调用审核

- 用户指定审核工具或方式时优先遵循；否则使用当前宿主可用的独立审核能力，并记录实际工具和方式。Claude Code 和 Codex 均可完成审核，不要求额外安装另一端，也不默认两端各审一次。
- 每轮向 reviewer 提供已确认的需求、验收条件、checklist 实施进度、变更边界及相关文档，明确审核全部未提交变更。逐步模式说明哪些项尚未实施，不把计划中尚未实施的项本身当作缺陷，但仍检查已有改动导致的回归和关联问题。无关既有变更也需审核，发现问题时单独标明归属，不要求为审核提前实现下一项。
- 全部已暂存、未暂存及未跟踪的内容都需覆盖，不能只提供 `git diff`，也不能按当前项或文件清单截取部分变更。reviewer 无法直接读取工作区时，提供完整差异、未跟踪文件内容和必要上下文；材料缺失时不能宣称完整审核通过。
- 除变更本身，还应沿受影响的用户入口读取必要的既有实现，核对组合后的行为与验收条件。显式提供支撑结论的相关测试工具和脱敏证据，包括被 Git 忽略的材料；审核材料与提交范围分别决定，不为审核强制提交环境数据或暴露凭据。
- reviewer 同时检查验收条件是否有缺口、检查方法能否识别错误结果、证据是否支持所声称的范围，不能只复算已有“通过”结果。迁移或跨版本适配按行为核实等价性，不能以同名模块、合并无冲突或语法通过代替。
- 审核同时检查改动与当前任务的对应关系，识别无关修改和缺乏需求依据的复杂度；不能只因个人风格偏好或代码行数较多就要求重写。
- reviewer 只读检查并报告问题，不修改文件、不提交、不再次启动审核循环。按宿主能力限制工具权限，修复由实现方完成；审核报告应说明实际范围、问题位置与依据、严重程度及未验证部分。模型或进程正常退出不代表审核通过。

按实际环境选择调用方式，不假定所有版本都提供相同命令：

- **Codex**：先检查 `codex review --help`。两种模式均优先使用 `codex review --uncommitted`。需要通过自定义提示提供需求文档位置和实施进度时，可用 `codex review -`，提示中必须明确读取相关文档并审核全部已暂存、未暂存及未跟踪内容，不得限定为当前项或部分文件。不假定自定义 prompt 能与 `--uncommitted` 组合使用，也不假定独立审核自动继承主会话中的需求上下文。
- **Claude Code**：在宿主允许委派时，可使用独立的只读 reviewer 子代理，明确传入上述审核上下文；不假定环境已预装名为 `code-reviewer` 的代理。支持独立 CLI 调用时，先检查 `claude --help`，可用 `claude -p` 传入审核提示，通过工具及权限配置限制写入，保留只读检查所需能力或提供完整材料。不要虚构 `claude review` 命令；宿主禁止嵌套会话时，使用其支持的审核能力或手动独立会话，不绕过限制。
- **手动交互**：用户选择手动方式时，在对应客户端的独立审核会话或可用审核入口中发起审核，取得真实结果后继续。`/review` 等交互命令须以当前客户端支持情况为准，不能当作通用 shell 命令。
- 所选审核方式不可用或结果无法获得时，记录受阻并说明可选替代方式；切换用户明确指定的工具前取得确认。普通自查不能冒充独立审核，也不能因缺少 Codex 就认定 Claude Code 无法审核。

### 处理每轮结果

1. 等待审核完整结束，读取真实结论并简要记录范围和发现。进程退出成功不等于没有问题。
2. 核实发现，以足以解决问题的最小必要改动修复本次任务已实现内容中的有效问题，包括此前已通过审核的项，并执行受影响的验证；不能借审核扩展功能或重做架构，也不能以控制改动为由保留有效问题。无关既有变更中的问题或需要改变需求、提前实现后续项的问题，记录后交用户决定，不擅自修改。
3. 对误报说明可复核的依据；不能自行降低严重程度、隐藏发现或以“不是阻塞级别”跳过有效问题。
4. 每次修复后，重新审核最新的全部未提交变更，不只复查当前项、修复涉及的文件或上轮指出的片段；两种模式的审核范围始终一致。
5. 仅当最新一轮完整审核全部未提交变更、没有待解决问题且必要验证通过，才进入人工审核。逐步模式到此必须暂停，等待用户确认下一项；全量模式到此交付全部结果。存在尚未澄清的争议或待用户决定的问题时不能标记审核通过。

- 不用固定轮数代替通过条件。若连续两轮出现同一问题且没有实质进展、修复互相冲突或需要用户决策，记录受阻并请求决定，不无限重试，也不宣称通过。
- 同类遗漏反复出现时，归纳共同原因并检查相关入口、配置或支持范围，重新评估当前方案与验收覆盖，避免只逐条修复报告中的实例。涉及共享实现或多版本时，评估新缺陷对相关分支及既往验收结论的影响，标明受影响、不适用或待核实；调查不自动授权修改其他分支或扩大功能范围。
- 文档中记录每轮简短结论即可。最终仅追加审核记录不触发记录自身的无限审核循环；代码、配置、需求或其他实质内容再次变化时必须重新审核。

## 5. 人工审核与授权交付

- 全部未提交变更的独立审核通过后标记“待人工审核”，提供需求文档、变更摘要、验证结果和最新审核结论，保留未提交变更供用户检查。逐步模式明确已完成的当前项和待确认的下一项，不能自动继续；最后一项通过后交付整体结果。
- 交付时单列本次为复用而进行的既有模块调整或重构，说明必要性、影响范围、原调用方行为是否保持及验证结果，包括自行完成的小调整；没有此类改动时不增加空栏目。验证结论保留适用条件与未覆盖项。
- “最新审核未发现问题”不等于证明没有缺陷，不用该表述替代人工审核。
- 用户提出修改时完成必要确认、实现及验证，重新对全部未提交变更进入审核循环，然后再次交由人工审核。
- 整体人工审核通过后，只有取得用户明确授权才执行 commit 或 push；分别按授权范围执行。确认进入下一项不等于授权提交。用户自行提交也是有效交付方式。
- 整体人工审核通过但未授权提交时记录“待授权提交”。交付状态以实际结果为准，不把单项完成、整体审核通过和已提交混为一谈。
